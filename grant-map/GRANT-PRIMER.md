# GRANT PRIMER

## What this document is

This document is a **grant-application primer for the Civic Infrastructure**.

It is not the grant application itself.

A grant application is always written for a particular funder, program, solicitation, deadline, budget, and scoring process. Those details change from one opportunity to another.

The Civic Infrastructure should not have to redefine itself every time an application is written.

This primer therefore establishes the stable material from which grant applications can be built:

- what the Civic Infrastructure is,
- what problem it addresses,
- why the problem matters,
- what is distinctive about the approach,
- what already exists,
- what the Grant is expected to enable,
- what kinds of outcomes can reasonably be claimed,
- what evidence belongs in an application,
- and how the project maps to ordinary grant language.

The objective is that a reader unfamiliar with the project can understand it without first learning its development history, network topology, PKI design, RAG architecture, HOA disputes, or source code.

---

# 1. The project in one paragraph

The **Civic Infrastructure** is a deliberately bounded technical and human infrastructure for civic participation, evidence, communication, trust, diagnostics, and resource coordination.

It is designed around a simple problem: many individuals and groups possess useful knowledge, time, technical ability, equipment, attention, compute, physical capacity, and willingness to contribute, but lack a direction they consider sufficiently credible, bounded, consequential, and trustworthy.

The Civic Infrastructure provides that direction by combining deliberate participation, explicit qualification, technical trust, human-operable services, evidence preservation, operational transparency, and clearly defined relationship boundaries.

It is infrastructure for civic activity.

It is not an activist platform.

---

# 2. The problem the Civic Infrastructure addresses

Many civic problems are described as shortages:

- not enough volunteers,
- not enough technical expertise,
- not enough public participation,
- not enough institutional transparency,
- not enough money,
- not enough time,
- not enough local knowledge,
- or not enough capacity.

The Civic Infrastructure begins from a different observation.

In many cases, useful capacity already exists.

People already possess:

- professional knowledge,
- technical skills,
- spare computing capacity,
- storage,
- tools,
- equipment,
- workshop space,
- organizational experience,
- local knowledge,
- time,
- attention,
- and a desire to make a positive difference.

The missing component is often not willingness.

It is **trusted direction**.

A person may be willing to contribute but unwilling to commit substantial effort to:

- an organization whose incentives are unclear,
- a platform whose rules can change without warning,
- a project whose boundaries are undefined,
- a movement whose objectives are political rather than operational,
- a system that cannot show what happened to contributed resources,
- or an institution that cannot demonstrate that individual effort produces a meaningful result.

The Civic Infrastructure is designed to turn that underused capacity into productive civic participation.

---

# 3. Surplus capacity

The project uses the term **surplus capacity**.

Surplus capacity is productive human, technical, physical, organizational, or economic capability that exists beyond its present use and whose holder is willing to employ it when a sufficiently credible and meaningful direction is available.

Examples include:

- an engineer with several hours each month available for a bounded technical problem,
- a retired professional with deep domain knowledge,
- a person with local institutional knowledge that is otherwise undocumented,
- unused compute or storage,
- workshop tools,
- physical space,
- a server with available capacity,
- administrative skill,
- postal and logistical effort,
- bandwidth,
- technical equipment,
- or simply the patience and attention required to complete work that consumer systems usually avoid.

The Civic Infrastructure treats this capacity as economically meaningful.

The core relationship is:

```text
existing ability
+ existing willingness
+ underused productive capacity
+ trusted direction
+ bounded purpose
+ observable consequence
=
productive civic participation
```

The Grant is therefore not principally intended to purchase participation.

It is intended to improve the mechanism that allows already-existing productive capacity to find credible civic work.

---

# 4. Why the infrastructure is deliberately bounded

The Civic Infrastructure is not designed as an unlimited public network.

Participation occurs inside deliberately bounded Civic projects.

A bounded project has:

- an explicit participation process,
- explicit qualification rules,
- its own technical trust domain,
- defined communications boundaries,
- defined relationship semantics,
- and a human-understandable purpose.

Kane County is the first concrete project.

The reusable idea, however, is not "a Kane County website."

The reusable unit is:

```text
deliberate participation
+ project qualification
+ project trust domain
+ bounded services
+ explicit relationships
+ operational evidence
+ human operability
```

This boundary is important for both grant credibility and project safety.

The system does not depend on unlimited growth to demonstrate value.

A small bounded project can be successful if it performs its intended civic function well.

# 5. SASE: participation begins with a deliberate human act

The first human participation gate is the **Self-Addressed Stamped Envelope (SASE)**.

Participation does not begin with a click, an imported mailing list, an automatically created account, or a public-record database.

It begins with an intentional act performed by the prospective participant.

The SASE provides observable evidence that the person:

- voluntarily elected to participate,
- expended some personal effort,
- committed a small amount of money,
- completed a physical multi-step process,
- accepted delay before receiving privileges,
- and, where an address qualification matters, successfully used the relevant physical delivery path.

The friction is intentional.

Consumer systems generally try to eliminate all delay and effort from enrollment.

The Civic Infrastructure preserves a small amount because participation is meant to be deliberate rather than impulsive.

SASE does **not** prove permanent identity, ownership, standing, expertise, truthfulness, or governance authority.

It proves something narrower and useful:

> The participant voluntarily completed a delayed, multi-step enrollment process before receiving participation privileges.

---

# 6. Participation is not the same as qualification

The Civic Infrastructure keeps several concepts separate.

### Participation

Did the human deliberately elect to participate?

SASE addresses this question.

### Project qualification

Why does the participant qualify for this particular bounded Civic project?

Project-specific rules answer this.

### Current relationship

Does the qualifying relationship exist now?

For Kane residential use, **CURRENT RESIDENT** is deliberately present-tense.

### Affected Status

Is the participant presently affected by the institution, rule, event, or issue being examined?

### Same and Equal

Does another participant occupy the same relevant peer relationship for the matter under examination?

### Technical trust

Which infrastructure is authorized to operate the bounded project?

A project intermediate CA beneath the Civic Infrastructure CA establishes this trust domain.

These categories are intentionally separate.

A technical certificate does not establish civic standing.

Participation does not automatically create project qualification.

Project qualification does not automatically create Affected Status.

Affected Status does not automatically create a Same-and-Equal relationship.

# 7. Civic activity is not activism

The Civic Infrastructure distinguishes **civic activity** from **activism or advocacy**.

This distinction is functional rather than ideological.

## Civic activity

Civic activity makes an existing civic relationship operational.

Examples include:

- determining an existing right,
- determining an existing responsibility,
- exercising an existing right,
- fulfilling an existing duty,
- requesting records already required by law or agreement,
- determining whether an established procedure was followed,
- documenting what actually occurred,
- comparing a written obligation with observed performance,
- and preserving evidence.

A current homeowner attempting to determine and exercise that homeowner's existing rights and responsibilities within an HOA is engaged in civic activity.

If many Same-and-Equal homeowners independently do the same thing, the activity does not become activism merely because more people participate.

## Activism or advocacy

Activism seeks to change a governing relationship, policy, allocation, law, tax level, institutional priority, or desired public outcome.

That activity may be entirely justified.

It is still different from the infrastructure function.

For example:

- determining how tax revenue was collected, allocated, and spent is civic and economic analysis;
- organizing to reduce taxation or change the allocation is advocacy.

The Civic Infrastructure can provide tools useful to both activities.

Those tools are included because of their demonstrated utility for civic activity, not because the infrastructure promotes an activist objective.

---

# 8. The Civic Infrastructure is logistics and economics

The Civic Infrastructure is best understood as **logistics and economics**.

It coordinates:

- people,
- trust,
- evidence,
- messages,
- services,
- finite resources,
- technical capacity,
- qualification,
- provenance,
- and bounded relationships.

It does not provide ideology.

It does not decide which political result is desirable.

It does not tell a participant what cause to support.

A project built on the infrastructure may pursue an activist purpose.

The infrastructure itself does not.

This distinction is important for a grant reviewer because it limits the claim being made.

The project is not asking a funder to endorse a political position.

It is asking the funder to evaluate an infrastructure for making civic relationships, evidence, resources, and operations more legible and usable.

---

# 9. Operational surfaces: showing systems as they actually operate

A central Civic Infrastructure principle is:

> **Expose systems as they operate, not merely as they are conceived, described, marketed, or intended.**

The infrastructure distinguishes:

- written rule,
- declared purpose,
- intended function,
- technical capability,
- actual operation,
- observed outcome,
- enforcement,
- and misuse.

This distinction applies to both institutions and technology.

## Example: written law

Suppose a statute establishes a right.

The Civic Infrastructure does not stop at the written text.

The relevant operating surface includes:

```text
WRITTEN RIGHT OR DUTY
        ↓
DEFINED PROCEDURE
        ↓
ACTUAL REQUEST OR ACTION
        ↓
ACTUAL INSTITUTIONAL RESPONSE
        ↓
AVAILABLE ENFORCEMENT
        ↓
OBSERVED RESULT
```

If the declared right and practical result diverge, the divergence is itself important evidence.

An enforcement gap does not erase the written right.

It reveals the conditions under which the right does or does not become operational.

The infrastructure does not have to decide that the law is defective, that an institution is corrupt, or that a policy must change.

It makes the operational gap visible.

## Example: technology

Useful technological capacities can be adapted to harmful purposes.

Identity systems, ranking systems, recommendation systems, account controls, telemetry, cryptographic transfers, and large-scale communications can all perform legitimate functions.

They can also be adapted to tracking abuse, deceptive manipulation, improper de-platforming, fraud, fabricated information, or cryptocurrency scams.

The Civic Infrastructure distinguishes the technological capacity from the use made of it.

This prevents the project from becoming either reflexively pro-technology or reflexively anti-technology.

# 10. Finite resource pools

The Civic Infrastructure treats money, labor, compute, storage, equipment, time, attention, and bandwidth as finite resource pools.

The important question is not simply how much exists.

The important questions include:

- where the resource came from,
- where it was allocated,
- when it became obligated,
- where it was spent or consumed,
- what was produced,
- whether the resource was sufficient,
- how demand changed,
- how efficiency changed,
- and whether the observed trend is sustainable.

The resource states are different:

```text
AVAILABLE
    ↓
COLLECTED
    ↓
ALLOCATED
    ↓
OBLIGATED
    ↓
SPENT
    ↓
EXHAUSTED FOR THAT USE
```

Collection is not consumption.

Allocation is not consumption.

Holding is not consumption.

Spending is consumption of the finite pool for that use.

This makes it possible to examine a public expenditure without beginning from the assumption that the expenditure is inherently too high or too low.

A large expenditure is not itself a defect.

The infrastructure instead makes visible:

- the amount,
- the source,
- the expenditure,
- the output,
- the trend,
- the return value,
- and the relationship between resources consumed and results produced.

That is economic observability rather than advocacy.

# 11. Technology is admitted by demonstrated civic utility

The Civic Infrastructure does not adopt technology because it is fashionable.

It does not adopt a technology because it is:

- decentralized,
- disruptive,
- open source,
- associated with a movement,
- commercially successful,
- heavily promoted,
- or attractive to funders.

The burden is on the technology to justify its presence.

The admission sequence is:

```text
EVIDENCED CIVIC NEED
        ↓
FUNCTIONAL REQUIREMENT
        ↓
TECHNOLOGY EVALUATION
        ↓
DEMONSTRATED PRODUCTIVE UTILITY
        ↓
ADMISSION
```

The Civic Infrastructure does not search for civic problems in order to justify an interesting technology.

This rule applies to:

- artificial intelligence,
- blockchains,
- cryptocurrencies,
- token systems,
- distributed storage,
- social platforms,
- PKI,
- postal systems,
- cryptographic ledgers,
- and other technologies.

If a blockchain, cryptocurrency, or token mechanism demonstrates a necessary and productive Civic Infrastructure function, it can be admitted for that function.

Until that utility is evidenced, it has no privileged place in the system.

A technology admitted for civic purposes may also be useful to activists.

That is secondary utility, not the infrastructure's purpose.

# 12. Technical trust

The root technical trust authority is the **Civic Infrastructure CA**.

A bounded Civic project operates beneath its own project intermediate CA.

```text
Civic Infrastructure CA
    |
    +-- Project Intermediate CA
    |       |
    |       +-- project service certificate
    |       +-- project service certificate
    |
    +-- another Project Intermediate CA
            |
            +-- project service certificate
```

Kane County operates as one bounded project under this model.

The project CA establishes technical trust in project services.

It does not establish participation, residency, Affected Status, Same and Equal status, Civic standing, or governance authority.

Technical trust is intentionally narrower than civic relationship.

# 13. Why the project is credible

A grant proposal is stronger when the funder is not being asked to finance an idea that exists only on paper.

The Civic Infrastructure is already represented by live, operated components.

The grant-map records verified infrastructure facts and human management paths rather than relying on diagrams alone.

Examples of the existing operational environment include:

- a Civic Infrastructure trust hierarchy,
- Kane project service identities,
- bounded email infrastructure,
- browser trust requirements,
- human management surfaces,
- LXD-based compute infrastructure,
- WireGuard-connected service paths,
- evidence-oriented RAG work,
- and an email-first human interface.

The purpose of grant funding is therefore not to prove that computers can be connected or that a prototype can be imagined.

The funding case is about increasing the usefulness, accessibility, reproducibility, legibility, and human value of an already-operating design.

# 14. What the Grant buys

A strong grant application does not merely describe what money will be spent on.

It explains **what becomes possible because of the expenditure**.

For the Civic Infrastructure, the Grant has leverage when it turns functioning infrastructure into infrastructure that other humans can confidently understand, use, evaluate, reproduce, and contribute to.

The funding case therefore concerns capabilities such as:

- human-facing usability,
- understandable onboarding,
- operational documentation,
- evidence-preserving workflows,
- clear diagnostics,
- recoverability,
- reproducibility,
- participant-facing services,
- trust that can be understood by non-specialists,
- and a visible relationship between contribution and consequence.

The key grant proposition is:

> The infrastructure already demonstrates the underlying model. Funding increases the number of people and bounded groups for whom that model becomes practical, understandable, and desirable.

That is different from paying indefinitely for ordinary operations.

# 15. What a grant reviewer will usually ask

Different funders use different forms, but most applications are variations of the same underlying questions.

## Need / problem statement

What problem exists?

For this project:

> Useful civic capacity often exists but lacks a trusted, bounded, operational mechanism through which it can be applied consequentially.

## Target population or beneficiaries

Who benefits?

The answer must be specific to the grant opportunity.

Possible beneficiaries can include participants in a bounded Civic project, organizations attempting to establish trustworthy civic processes, or groups possessing useful surplus capacity.

A grant application should not claim "everyone" as the beneficiary.

## Proposed solution

What is being offered?

The Civic Infrastructure provides a bounded technical and human framework for participation, qualification, trust, communication, evidence, diagnostics, resource coordination, and human operation.

## Activities

What work will actually be performed with the grant?

This is funder-specific and belongs in the eventual application.

Activities are concrete actions, not aspirations.

Examples of the distinction:

```text
ACTIVITY:
Build and test a participant-facing workflow.

NOT AN ACTIVITY:
Improve civic engagement.
```

## Outputs

What directly countable things will the funded work produce?

Examples of output types:

- implemented interfaces,
- documented workflows,
- completed tests,
- operating services,
- participant onboarding events,
- replicated deployments,
- published technical documentation,
- or validated recovery procedures.

Outputs are usually things the project produces directly.

## Outcomes

What changes because those outputs exist?

Examples of outcome types:

- reduced onboarding difficulty,
- increased successful participant completion,
- improved recoverability,
- more independently operated deployments,
- improved evidence traceability,
- or greater productive use of surplus capacity.

Outputs and outcomes are not the same.

```text
OUTPUT:
A working participant portal.

OUTCOME:
Qualified participants can successfully complete a civic workflow without operator intervention.
```

## Evidence

Why should the reviewer believe the project can work?

Evidence can include:

- operating infrastructure,
- demonstrations,
- verified service paths,
- test results,
- repositories,
- documented workflows,
- completed prototypes,
- observed user behavior,
- comparative data,
- and independently verifiable public facts.

## Evaluation

How will success be measured?

A good measure is observable and connected to the claimed outcome.

Weak:

> Users will like the system.

Stronger:

> A defined percentage of qualified participants can complete the workflow without administrator intervention.

## Sustainability

What happens after the grant?

A funder wants to know whether the project disappears when grant money ends.

For the Civic Infrastructure, sustainability is connected to:

- bounded operating costs,
- reproducibility,
- surplus capacity,
- human-operable infrastructure,
- documented recovery,
- and avoidance of unnecessary technical dependency.

## Budget

What resources are required, and why?

A budget is not simply a list of purchases.

Every significant cost should connect to an activity and a result.

## Risk

What could prevent success?

Credible applications acknowledge technical, operational, adoption, governance, and dependency risks.

The purpose of a risk section is not to make the project appear weak.

It demonstrates that the applicant understands the operating surface rather than presenting an idealized system.

# 16. Outputs, outcomes, and impact

These three terms are frequently confused.

## Output

Something the funded project directly produces.

Examples:

- software,
- documentation,
- a deployed service,
- a training package,
- a completed integration,
- a tested workflow.

## Outcome

A measurable change enabled by the output.

Examples:

- participants complete onboarding more successfully,
- operators recover services with less undocumented knowledge,
- civic evidence becomes easier to verify,
- another bounded group reproduces a deployment.

## Impact

The larger long-term consequence.

Examples can include:

- more productive civic participation,
- better use of underused local capacity,
- stronger institutional observability,
- or more resilient bounded civic infrastructure.

A grant application should be careful with impact claims.

The farther the claimed result is from the funded activity, the more difficult causation becomes to establish.

The Civic Infrastructure should prefer measurable claims over grand claims.

---

# 17. What the application should not claim

The project does not need exaggerated language to be compelling.

A grant application should not imply that the Civic Infrastructure:

- solves democracy,
- fixes government,
- eliminates institutional failure,
- guarantees truthful participants,
- eliminates abuse,
- replaces law,
- replaces courts,
- replaces government,
- guarantees civic consensus,
- makes every participant equal,
- or automatically produces activism or reform.

Its strength is narrower and more defensible.

It makes civic relationships, evidence, operational surfaces, finite resources, technical trust, and human participation more explicit and usable.

That is sufficient.

# 18. Why smallness is an advantage

The Civic Infrastructure has been repeatedly reduced rather than expanded.

This is an advantage when the result is a smaller system that preserves the necessary function.

Grant proposals often become less credible when every useful idea is added to the project.

The Civic Infrastructure takes the opposite approach:

- bounded projects instead of universal membership,
- explicit qualification instead of vague community,
- deliberate participation instead of frictionless enrollment,
- demonstrated technology need instead of technology accumulation,
- human-operable infrastructure instead of hidden complexity,
- and evidenced functions instead of aspirational feature lists.

The design objective is not to demonstrate how much can be built.

It is to make the necessary system close to trivial to understand.

# 19. Grant leverage

The strongest funding argument is not that the project needs money.

Most projects need money.

The stronger question is:

> **What does one grant dollar unlock that otherwise remains difficult to achieve?**

For the Civic Infrastructure, leverage comes from converting existing assets into wider practical usefulness.

Existing assets include:

- operating infrastructure,
- technical design,
- working trust relationships,
- software,
- domain knowledge,
- project experience,
- surplus technical capacity,
- and a functioning bounded-project model.

Grant resources can have disproportionate value when applied to the interfaces between those assets and human use:

- comprehension,
- onboarding,
- documentation,
- demonstration,
- replication,
- evaluation,
- recovery,
- and participant experience.

This is why the Grant is not primarily a request to create a system from zero.

It is a request to increase the productive reach of an existing system.

# 20. How to read a grant opportunity

Before writing an application, extract the funder's requirements into a simple table.

| Question | What to identify |
| --- | --- |
| Who can apply? | Eligible applicant type |
| What does the funder want? | Program purpose |
| What will they pay for? | Eligible activities and expenses |
| What will they not pay for? | Exclusions |
| How much is available? | Award range |
| How long can the project run? | Performance period |
| What geographic area qualifies? | Geographic restrictions |
| Who must benefit? | Required population |
| What must be measured? | Evaluation requirements |
| What attachments are required? | Budget, letters, registrations, etc. |
| How is it scored? | Review criteria and weights |
| When is it due? | Deadline and submission method |

The grant application is then built to answer that funder's questions using the stable project material in this primer.

The project should not be distorted to fit a grant whose purpose does not match it.

A poor fit remains a poor fit even if the application can be made linguistically persuasive.

# 21. Basic grant vocabulary

**Applicant**  
The legal person or organization submitting the application.

**Funder / Grantmaker**  
The organization providing the grant.

**Solicitation / Notice of Funding Opportunity / RFP**  
The document describing the funding opportunity and application rules.

**Eligibility**  
The requirements determining who may apply.

**Allowable cost**  
An expense the grant permits.

**Match / Cost share**  
Resources the applicant must contribute in addition to the grant, when required.

**In-kind contribution**  
Non-cash resources contributed to the project, such as donated labor, equipment, or space, when the grant permits them to be counted.

**Performance period**  
The period during which funded work is performed.

**Deliverable**  
A specific item or result the grant requires.

**Milestone**  
A defined point showing progress.

**Output**  
A direct product of funded activity.

**Outcome**  
A measurable change resulting from the work.

**Impact**  
A broader long-term effect.

**Logic model**  
A structured relationship among resources, activities, outputs, outcomes, and impact.

**Evaluation**  
The method used to determine whether the project achieved its objectives.

**Sustainability**  
How useful operation or benefits continue after the grant period.

**Budget narrative / budget justification**  
The explanation connecting requested costs to project activities and outcomes.

**Indirect cost**  
Administrative or overhead cost not attributable to one project activity, subject to the funder's rules.

**Letters of support**  
Statements from relevant organizations or individuals demonstrating interest, credibility, partnership, or need.

# 22. A simple Civic Infrastructure logic model

A grant application will often require some version of a logic model.

For the Civic Infrastructure, the high-level structure is:

```text
INPUTS
    existing infrastructure
    technical expertise
    domain knowledge
    surplus capacity
    grant resources

        ↓

ACTIVITIES
    funder-specific implementation work

        ↓

OUTPUTS
    operating interfaces
    documented workflows
    verified services
    reproducible procedures
    tested participant functions

        ↓

OUTCOMES
    easier human operation
    easier participation
    stronger evidence traceability
    greater recoverability
    more productive use of surplus capacity
    greater reproducibility

        ↓

LONG-TERM IMPACT
    credible bounded civic infrastructure
    that people and groups can actually use,
    operate, evaluate, and reproduce
```

The exact activities, outputs, measures, and targets must come from the specific grant application.

# 23. The evidence discipline

Grant language should never outrun evidence.

The Civic Infrastructure already follows an evidence rule operationally: unknowns remain unknown until verified.

Grant writing should follow the same rule.

A proposal should distinguish:

- **verified fact** — directly supported,
- **demonstrated capability** — shown to operate,
- **measured result** — supported by data,
- **reasonable objective** — intended result of funded work,
- **hypothesis** — proposition to be tested,
- and **future possibility** — not yet established.

This distinction protects credibility.

A reviewer should be able to tell what already exists and what funding is expected to change.

# 24. The central grant case

The Civic Infrastructure does not begin with the premise that civic capacity must first be created.

It begins with the observation that substantial productive capacity already exists but often lacks a trustworthy direction.

The project provides:

- deliberate participation,
- bounded qualification,
- technical trust,
- operational transparency,
- evidence,
- resource visibility,
- communication,
- human management,
- and a credible relationship between contribution and consequence.

The Grant increases the usefulness of that mechanism.

The central funding proposition is therefore:

> **There is already useful human and technical capacity seeking consequential work. There is already a functioning Civic Infrastructure model capable of directing that capacity. Grant funding creates leverage by making the model easier to understand, use, verify, operate, and reproduce.**

That is the foundation from which a specific grant application can be written.
